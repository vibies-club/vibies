# D1 application schema

`migrations/` is the ordered D1 migration history and the only database schema
for production (`vibies-production`). It was ported from the retired PostgreSQL
schema ([D-033](../docs/DECISIONS.md#d-033-retire-vercel-and-supabase)). Applied
migrations never change; add a new numbered file instead. Run the isolated
schema checks with Node 24:

```sh
node --test tests/d1-schema.test.mjs
```

The migrations retain all ten application tables. The former `vibies_private`
and `public` schema prefixes become unprefixed SQLite table names; this does not
make the private tables public. Only the Worker binding may query them, and the
application adapter must apply current-session authorization inside mutations.
D1 does not provide the PostgreSQL role or SECURITY DEFINER boundary.

| Source type or behavior | D1 representation |
| --- | --- |
| UUID primary and foreign keys | Text, preserving the source ID; new IDs generated by the application |
| GitHub and repository IDs | Text, never converted to JavaScript numbers |
| `timestamptz` | UTC text retaining the imported fractional precision |
| Boolean | Integer constrained to 0 or 1 |
| Identity bigint | `INTEGER PRIMARY KEY AUTOINCREMENT`; explicit imported IDs advance allocation |
| Nickname uniqueness | Explicit `nickname_key` and `instructor_nickname_key`, plus cross-table guards |
| Deferred milestone position uniqueness | Immediate unique `(project_id, position)`; atomic replacement for reorder |
| Session authentication provenance | `auth_provider`: `legacy` (import/default), `github`, or `google` |

Importers must emit UTC instants consistently and compare their exact canonical
values during reconciliation. Do not round source timestamps to milliseconds.
JavaScript number results cannot safely represent integers above 2^53 - 1;
reconciliation must check identity/version ranges before an adapter converts
these values. An expired imported session remains expired. `legacy` never proves
a recent GitHub login for Google linking.

Nickname keys are supplied by the trusted normalization layer, not SQLite
`lower()`, which is ASCII-only. Derive keys using the source-compatible Unicode
lowercase behavior after its existing space trim and character validation.
Do not add Unicode normalization or locale-dependent casing without checking
source collisions. Both approved and revoked Members reserve their keys. The
Instructor reserves a key in the same namespace. The existing application text,
URL, hash and nickname validators remain required; portable SQL checks alone
are not replacements for PostgreSQL's Unicode-aware helper functions.

SQLite enforces member/project capacity and the 20 available unique milestone
positions. Every mutation still needs the exact authorization, status, expiry,
ownership and expected-version conditions in the write itself. Batch statements
must be linked by a guaranteed successful guard; a zero-row update does not roll
back D1 batches automatically. Constraint failures abort the batch. Publish must
atomically set the permanent onboarding milestone. The schema does not
implicitly mark imported published projects as newly onboarded.

For milestone reordering, read the exact current records, then use one guarded
atomic batch to delete the affected records and reinsert them in final positions.
Preserve IDs and content; preserve source timestamps for imports and set the
operation's expected update timestamps for user edits. This avoids unsupported
deferred uniqueness and temporary out-of-range positions. Increment the parent
version in the same guarded transaction. Never issue the delete and inserts in
separate requests.

`deployment_activation` begins `disabled`. Only an operator reconciliation
procedure may advance it to `reconciled` and then `active`, with environment,
snapshot and timestamp evidence. New builds must preserve this row. Private
reads and all application writes must explicitly require `active`; migrations
and the controlled importer can populate a disabled database. The migration
itself does not activate a database. A missing row must also fail closed.

Google identity and Better Auth tables require the pinned integration's actual
schema and are added by a separate migration once that contract is validated.
Do not infer account links from emails or add guessed provider schemas here.

Validation here covers schema and SQLite transaction behavior with synthetic
fixtures, including competing capacity approvals. It does not by itself prove
Workers execution, full PostgreSQL operation parity, or live reconciliation.

Official D1 references checked on 2026-10-15:

- [Foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/):
  D1 enforces foreign keys on every query and migration.
- [Database binding and batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/):
  batch statements execute transactionally and failures roll the batch back.
